# 소비 통제 화면과 계산

주요 메뉴는 현황, 기록, 결제수단, 설정이다. 기존 분석과 추천 계획은 기본 메뉴에서 숨기며 과거 자료·백업·복구·계정 기능은 보존한다.

## 월과 거래의 구분

- 카드 소비는 카드별 사용 마감일과 결제일로 계산한 **명목 청구월**에 한 번 반영한다. 다음 청구월 예정액은 따로 보여준다.
- 입금·체크카드·현금·계좌지출과 실제 고정지출은 기존 가계부 집계 기간 및 명시한 귀속월을 유지한다. 집계 기간은 설정에서 변경할 수 있으며 화면의 상세 계산에 표시한다.
- 여유자금 = 실제 유효 입금 − 실제 기록된 고정지출 − 해당 청구월 변동소비. 예정 수입과 미납 고정지출은 합계에 넣지 않는다. 고정지출은 소비한도에 다시 넣지 않는다.
- 카드대금은 `transfer` 거래와 납부 연결로 관리한다. 기존 출금과 연결할 수 있고 새 소비를 만들지 않는다. 실제 출금과 청구가 다르면 차이와 조정 이력을 보존한다.
- 청구기간이 미설정인 신용카드는 사용일 기준 임시 합계와 설정 요청을 표시한다. 실제 카드사 자료를 자동 조회하지 않는다.

## 보존과 변경

`productVersion: 4` 변환은 원거래를 보존하고 `transactionControl`에 결제수단 ID와 청구조건 스냅샷을 추가한다. 기존 v3 상태는 IndexedDB `pre-v4-backup`에 저장한다. 결제수단 이름 변경·확인된 병합 후에도 ID와 납부 연결, 이미 저장된 청구조건을 유지한다. 거래일·금액·할부·직접 청구월을 수정하면 관련 계산을 갱신한다.

`cardSettlements`, `billAdjustments`, `fixedPayments`, `incomeReviews`, `limitHistory`는 기존 공동가계부 JSON 안에 저장한다. 같은 기록의 동시수정은 충돌 확인 대상으로 처리한다. Supabase 테이블·인증·권한·RLS는 변경하지 않는다.

중복 의심 입금은 사용자가 결정하기 전까지 모두 유지한다. 확인된 중복은 원본을 보관하고 합계에서 제외하며 거래 상세에서 복원할 수 있다. 외부 거래 ID 또는 날짜·시간·금액·계좌·거래처를 비교하는 무료 규칙 방식이다. 카테고리도 사용자 규칙과 내장 규칙을 사용하며 AI 모델이나 유료 API를 사용하지 않는다.

실제 고정지출 납부를 확인하면 다음 달 예정액만 갱신한다. 다음 달 수동 금액이 있으면 수동 설정이 우선하며 다음 달을 납부완료로 만들지 않는다.

## 청구 세부사항

할부는 원 단위를 보존하는 균등 분할로 월별 배분한다. 카드사 수수료·할인·환불과 별도 청구 일정은 거래의 직접 청구월 및 조정 내역으로 맞춘다. 휴일 보정은 주말과 사용자가 입력한 휴일 목록을 적용하며 공휴일 자동 수집은 하지 않는다. 휴일로 실제 출금일이 다른 달로 넘어가도 원래 명목 청구월은 보존한다.

## 검증과 배포

`pnpm test`는 계산·보존·동시수정·기존 기능을 검증한다. `qa/control-browser.mjs`는 독립 Chromium과 iPhone WebKit, PWA 오프라인에서 입력·수정·납부·한도·재접속·배지를 검증한다. Supabase 요청을 차단하고 가상 자료만 브라우저 저장소에 넣는다. 실제 iPhone 하드웨어 검증과는 구분한다.

GitHub Pages는 `main / (root)`를 게시한다. `RichKkok quality checks`는 회귀검사와 생성된 오프라인 캐시를 확인하고, main에서는 공개 사이트의 캐시가 해당 소스와 같은지 기다린 뒤 같은 가상 자료로 운영 화면을 검증한다. 금융 원문이나 테스트 자료를 운영 데이터베이스에 쓰지 않는다.
